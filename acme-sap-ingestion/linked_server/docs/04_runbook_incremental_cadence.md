# Runbook — SAP→raw_sap ingestion with cadence derived from the dbt DAGs

Implementation runbook **and** architecture documentation. The `.sql` artifacts are
generated by `_generator/generate_sql.py`; **you execute** each step in the database (SSMS/sqlcmd).

## Why
The ingestion was migrated to a linked server (`OPENQUERY HANA_LINK`) + SQL Agent, but everything
was `full_reload`. dbt runs at different cadences; **each table's ingestion cadence must
follow the DAG that consumes it** — otherwise running the DAG several times a day is
pointless (it reprocesses stale data). Since an hourly full_reload would lock up the production
HANA, the heavy tables updated intraday use the **natural incremental strategy**
from `tables.yaml` (mirroring the strategies of the previous Python pipeline).

## Cadences (from the dbt DAGs, BRT)
| SQL Agent job | When | DAG it serves | Tables | Strategy |
|---|---|---|---|---|
| `ingestion_hourly` | 06:30→21:30 (hourly) | `comum`+`sales` | group `hourly` (20 light dims/sales) + 3 families | dims full; header upsert; rows via_header |
| `ingestion_inventory` | 06:30,09:30,…,21:30 (every 3h) | `estoque` (7,10,13,16,19,22) | `usp_ing_OINM` + group `inventory` (OITW, ITM1) | OINM upsert; OITW/ITM1 full |
| `ingestion_daily_movement` | 04:00 | `mov_diaria` (5h) | `usp_ing_OINM` | upsert |
| `ingestion_purchases` | 05:00 | `compras_fin` (6h) | group `purchases` (7) | full (1×/day) |
| `ingestion_nightly` | 03:00 | no scheduled consumer | `usp_ing_JDT1`+`usp_ing_OJDT` + group `nightly` (10) | append/full |

## Strategy by table_name
- **incremental_upsert** (dedicated proc): OINV, OQUT, ORDR (family headers); OINM (`usp_ing_OINM`).
- **incremental_via_header** (within the header's family): INV1/INV6/INV12 (OINV); QUT1/QUT12 (OQUT); RDR1 (ORDR).
- **incremental_append**, idempotent (dedicated proc): JDT1, OJDT.
- **full_reload** (generic group `usp_ingest_group`): everything else (dims, purchases, inventory OITW/ITM1, orphans). `source_strategy` in meta preserves the natural strategy from the yaml.

Families (`02_procs/dedicated/`): `usp_ing_fam_sales_invoice` (OINV+INV1+INV6+INV12), `usp_ing_fam_quote`
(OQUT+QUT1+QUT12), `usp_ing_fam_sales_order` (ORDR+RDR1). Each family **pre-captures the header watermark
BEFORE reloading it** (critical sort_order) and uses it in the header upsert and in the rows' via_header.

## Risks / notes
1. **OITW/ITM1 without watermark** — full 6×/day; validate HANA (Phase 5). Physical limit.
2. **Future RefDate** in JDT1/OJDT pins the append watermark (inherited from Python).
3. **Atomicity** — incremental does DELETE+INSERT in the same `BEGIN TRAN`+`XACT_ABORT` (no TRUNCATE).
4. **Family** — header and rows in independent transactions; `@retry_attempts=1` on the job mitigates a row-failure-after-header-commit.
5. **`ingestion_hourly` multi-step** — `@on_fail_action=2` (quit failure): if a step fails, the cycle stops and alerts; the next cycle (1h later) resumes.
6. **ORIN/RIN1/RIN12** stay full in group `hourly` (they are small); if they grow, promote to a family (ORIN header) by editing `tables.yaml` + the generator.

## Proc mechanics (reference)
Frame: `XACT_ABORT ON` → `sp_getapplock` Exclusive/Session → log `running` → `BEGIN TRAN` … `COMMIT`
→ log `success`; `CATCH`: `ROLLBACK` + log `error` + `releaseapplock` + `THROW`. OPENQUERY requires a literal →
`sp_executesql` (`#d` via `SELECT INTO` + DELETE + INSERT + `@@ROWCOUNT` in the same string, `@out OUTPUT`).
Watermark read from `raw_sap` itself (`MAX`/`TOP 1`); null → no WHERE (falls back to full). Dates `CONVERT(...,23)`.
